# 🧭 Git/GitHub 협업 가이드

이 문서는 **Private 저장소 + Collaborator(협업자) 방식**으로 작업하는 우리 팀을 위한 가이드입니다.
우리는 Fork를 사용하지 않고, 모두가 원본 저장소에 직접 접근해서 **브랜치를 따서** 작업합니다.

> 💡 이 문서는 위에서부터 순서대로 따라 하면 됩니다. 막히는 부분이 있으면 맨 아래 **트러블슈팅** 섹션을 먼저 확인해 보세요!

## 🚀 [초기 설정] 레포지토리 가져오기

우리 프로젝트는 **Private 저장소**이고 팀원 모두가 **Collaborator(협업자)**로 등록되어 있습니다.
그래서 Fork(내 계정으로 복사)를 할 필요 없이, **원본 저장소를 바로 clone** 하면 됩니다.

> ⚠️ 시작하기 전에, 저장소 관리자에게 GitHub 아이디를 알려주고 **Collaborator로 초대**를 받아야 합니다. 초대 이메일의 "Accept invitation"을 먼저 눌러주세요.

```bash
git clone <Repo-URL>       # 원본 저장소를 내 컴퓨터로 통째로 복사해온다
cd <저장소-폴더명>          # 방금 받은 프로젝트 폴더로 이동한다
```

처음 한 번만 아래 명령어로 내 이름과 이메일을 설정해 주세요. (커밋에 "누가 했는지" 기록됩니다)

```bash
git config --global user.name "내이름"          # 커밋에 표시될 이름 설정
git config --global user.email "내이메일@example.com"  # 커밋에 표시될 이메일 설정
```

## 🔁 [기본 작업 흐름] 하루 일과처럼 따라 하는 Git 루틴

작업을 시작할 때마다 아래 순서를 **그대로** 반복하면 됩니다. 출근해서 커피 내리듯 습관처럼 따라 해보세요 ☕

### 1️⃣ 작업 시작 전, 최신 코드 받아오기

다른 팀원이 이미 작업해서 올린 내용이 있을 수 있으니, **작업을 시작하기 전엔 항상** 최신 코드를 받아옵니다.

```bash
git switch main            # main 브랜치로 이동한다 (내 작업 브랜치가 아닌 기준 브랜치)
git pull origin main        # 원격 저장소(GitHub)의 main 브랜치 최신 내용을 로컬로 가져온다
```

### 2️⃣ 나만의 작업 브랜치 만들고 이동하기

`main` 브랜치에 직접 코드를 작성하지 않습니다! 항상 **새 브랜치**를 만들어서 그 위에서 작업합니다.

```bash
git switch -c feature/기능이름    # feature/기능이름 브랜치를 새로 만들면서 그 브랜치로 이동한다
# 또는 (구버전 명령어, 결과는 동일합니다)
git checkout -b feature/기능이름  # feature/기능이름 브랜치를 새로 만들면서 그 브랜치로 이동한다
```

**브랜치 이름 예시**

| 브랜치 이름 | 용도 |
|---|---|
| `feature/login` | 로그인 기능 개발 |
| `fix/upload-error` | 업로드 버그 수정 |
| `docs/readme-update` | 문서 수정 |

### 3️⃣ 코드 수정 후 상태 확인 & 임시 저장(스테이징)

코드를 수정했다면, 어떤 파일이 바뀌었는지 확인하고 커밋할 준비를 합니다.

```bash
git status          # 지금까지 어떤 파일이 수정/추가/삭제됐는지 확인한다
git add .            # 변경된 모든 파일을 커밋 대상(스테이징 영역)으로 올린다
```

> 💡 특정 파일만 올리고 싶다면 `git add .` 대신 `git add 파일이름` 을 사용하세요.

### 4️⃣ 의미 있는 단위로 커밋 기록하기

`git add` 로 올린 변경사항에 "이건 무슨 작업이다"라는 메시지를 붙여서 저장합니다.

```bash
git commit -m "feat: 로그인 기능 구현"    # 변경사항을 하나의 기록(커밋)으로 저장한다
```

**🏷️ 초보자를 위한 커밋 태그 가이드**

커밋 메시지 앞에 아래 태그를 붙이면, 나중에 히스토리만 봐도 무슨 작업인지 한눈에 파악할 수 있어요.

| 태그 | 의미 | 예시 |
|---|---|---|
| `feat` | 새로운 기능 추가 | `feat: 검수 페이지 필터 기능 추가` |
| `fix` | 버그 수정 | `fix: 엑셀 다운로드 시 한글 깨짐 수정` |
| `refactor` | 기능 변화 없이 코드 구조 개선 | `refactor: DashboardPage 컴포넌트 분리` |
| `docs` | 문서 수정 (README, 주석 등) | `docs: Git 협업 가이드 추가` |
| `style` | 코드 포맷팅, 세미콜론 등 (동작 변화 없음) | `style: 들여쓰기 정리` |
| `test` | 테스트 코드 추가/수정 | `test: 로그인 API 테스트 추가` |
| `chore` | 빌드 설정, 패키지 설치 등 잡일 | `chore: eslint 설정 추가` |

> 💡 커밋은 너무 크게 한 번에 하지 말고, **의미 있는 작업 단위**로 자주 나눠서 하는 게 좋아요. (예: "로그인 기능 완성" 하나보다 "입력 폼 만들기" → "유효성 검사 추가" → "API 연동" 처럼 나누기)

### 5️⃣ 내 브랜치를 원격(GitHub)에 올리기

내 컴퓨터에만 있던 커밋을 GitHub 저장소로 올려서, 팀원들이 볼 수 있게 합니다.

```bash
git push origin feature/기능이름    # 내 로컬 브랜치를 GitHub의 같은 이름 브랜치로 올린다
```

> 💡 처음 push하는 브랜치라면 GitHub가 새 브랜치를 자동으로 만들어줍니다. 걱정하지 마세요!

## 🌐 [GitHub 웹사이트 작업] Pull Request(PR) 보내기

브랜치를 원격에 올렸다면, 이제 **"이 코드를 main에 합쳐줘"** 라고 요청할 차례입니다. 이 요청을 **Pull Request(PR)** 라고 부릅니다.

1. **GitHub 저장소 페이지로 이동**합니다.
2. 방금 push한 브랜치를 올렸다면 상단에 **"Compare & pull request"** 버튼이 자동으로 나타납니다. (안 보이면 좌측 상단 `Pull requests` 탭 → `New pull request` 클릭)
3. **base**는 `main`, **compare**는 내가 작업한 `feature/기능이름` 브랜치로 설정합니다.
   - 즉, "내 브랜치의 변경사항을 main에 반영하고 싶다"는 방향입니다.
4. 제목과 설명에 **무슨 작업을 했는지** 간단히 적어줍니다. (커밋 메시지를 참고해서 작성하면 편해요)
5. 오른쪽 **Reviewers** 항목에서 리뷰를 받을 팀원을 지정합니다.
6. **Create pull request** 버튼을 눌러 PR을 생성합니다.
7. 팀원이 코드를 확인하고 **Approve(승인)** 하거나 **코멘트로 수정 요청**을 남깁니다.
   - 수정 요청이 있다면 내 컴퓨터에서 코드를 고치고 다시 `git add` → `git commit` → `git push` 하면 **같은 PR에 자동으로 반영**됩니다. (PR을 새로 만들 필요 없어요!)
8. 승인을 받으면 **Merge pull request** 버튼을 눌러 `main`에 병합합니다.
9. 병합이 끝난 브랜치는 **Delete branch** 버튼으로 정리해주세요. (깔끔한 저장소 유지를 위해)
10. 내 컴퓨터에서도 아래처럼 마무리합니다.

```bash
git switch main             # main 브랜치로 돌아온다
git pull origin main         # 방금 merge된 최신 내용을 받아온다
git branch -d feature/기능이름  # 다 쓴 로컬 브랜치를 정리(삭제)한다
```

## 🆘 [트러블슈팅] 초보자가 무조건 겪는 3가지 상황 해결법

### 😱 상황 1. "main 브랜치에 직접 커밋해 버렸어요! 어떻게 옮기나요?"

당황하지 마세요! 아직 `push` 하지 않았다면 아래 방법으로 방금 만든 커밋을 새 브랜치로 그대로 옮길 수 있습니다.

```bash
git branch feature/기능이름        # 현재 위치(main)에 있는 커밋을 포함한 새 브랜치를 만든다
git reset --hard origin/main       # main 브랜치를 원격 기준으로 되돌린다 (방금 만든 커밋은 사라진 것처럼 보이지만 새 브랜치에는 남아있음)
git switch feature/기능이름         # 커밋이 살아있는 새 브랜치로 이동한다
```

> ⚠️ `git reset --hard` 는 **커밋되지 않은 변경사항을 날리는 위험한 명령어**입니다. 위 순서(branch 먼저 생성 → reset)를 지키면 안전하지만, 순서가 헷갈리면 팀원에게 먼저 물어보세요.

이제 `git status` 로 확인해보면 main은 깨끗하고, 내 커밋은 `feature/기능이름` 브랜치에 안전하게 있을 거예요. 이 상태에서 [5️⃣ push 하기](#5️⃣-내-브랜치를-원격github에-올리기)부터 이어서 진행하면 됩니다.

### 😵 상황 2. "코드가 충돌(Conflict) 나서 머지가 안 돼요! VS Code에서 어떻게 해결하나요?"

**충돌(Conflict)** 은 같은 파일의 같은 부분을 나와 다른 사람이 동시에 수정했을 때 발생합니다. 흔한 일이니 걱정하지 마세요!

**1. 먼저 최신 main을 내 브랜치로 가져옵니다.**

```bash
git switch feature/기능이름   # 내 작업 브랜치로 이동한다
git pull origin main         # 최신 main 내용을 내 브랜치로 가져와서 합쳐본다
```

**2. 충돌이 발생하면 터미널에 아래처럼 표시됩니다.**

```bash
CONFLICT (content): Merge conflict in src/App.tsx
```

**3. VS Code로 충돌 파일을 엽니다.** VS Code가 충돌 부분을 아래처럼 자동으로 표시해줍니다.

```
<<<<<<< HEAD
내가 수정한 코드
=======
다른 사람이 수정한 코드
>>>>>>> origin/main
```

**4. VS Code 화면에서 충돌 블록 바로 위에 뜨는 파란색 버튼을 클릭해서 선택합니다.**

- `Accept Current Change` → 내 코드만 남기기
- `Accept Incoming Change` → 상대방 코드만 남기기
- `Accept Both Changes` → 둘 다 남기기
- 또는 직접 코드를 수정해서 `<<<<<<<`, `=======`, `>>>>>>>` 표시를 **모두 지우고** 원하는 최종 코드만 남겨도 됩니다.

> 💡 어떤 걸 선택해야 할지 모르겠다면, 그 코드를 작성한 팀원에게 먼저 물어보고 결정하세요!

**5. 충돌을 다 해결했다면, 다시 커밋합니다.**

```bash
git add .                          # 충돌을 해결한 파일을 다시 스테이징한다
git commit -m "fix: main 병합 충돌 해결"   # 충돌 해결 내용을 커밋으로 남긴다
git push origin feature/기능이름     # 해결된 내용을 원격에 올린다
```

### 😭 상황 3. "실수로 작업 중인 코드를 다 날린 것 같아요. 복구 가능한가요?"

상황에 따라 복구 방법이 다릅니다. 아래에서 내 상황에 맞는 걸 찾아보세요.

**Case A. `git add` 하기 전에 파일 내용을 실수로 수정/삭제했어요.**

```bash
git status                    # 어떤 파일이 수정된 상태인지 확인한다
git restore 파일이름            # 해당 파일을 가장 최근 커밋 상태로 되돌린다 (수정 내용 사라짐 주의!)
# 모든 파일을 되돌리고 싶다면:
git restore .                 # 모든 파일을 가장 최근 커밋 상태로 되돌린다
```

**Case B. `git commit` 은 했는데, 그 이후 내용을 날렸어요.**

커밋만 되어 있다면 절대 사라지지 않습니다! 아래 명령어로 확인 가능해요.

```bash
git log --oneline             # 지금까지의 커밋 목록을 한 줄씩 확인한다
git restore --source=<커밋해시> 파일이름   # 특정 커밋 시점의 파일 내용으로 되돌린다
```

**Case C. `git reset --hard` 를 잘못 눌러서 커밋 자체가 사라진 것 같아요.**

Git은 최근 삭제된 커밋도 당분간 보관합니다. `reflog` 로 되찾을 수 있어요.

```bash
git reflog                    # 최근에 내가 했던 모든 Git 작업 이력을 확인한다 (사라진 커밋도 여기 남아있음)
git reset --hard <되돌리고싶은-커밋해시>   # 원하는 시점의 커밋으로 완전히 되돌린다
```

> ⚠️ 위 세 가지 방법 모두 **되돌리기 전에 현재 상태를 한 번 더 확인**하세요. 특히 `git reset --hard` 는 실행 취소가 어려우니, 확신이 없다면 먼저 팀원에게 화면을 공유하고 물어보는 걸 추천합니다.

## 📎 요약 치트시트

```bash
git switch main               # main으로 이동
git pull origin main           # 최신 코드 받기
git switch -c feature/이름      # 새 브랜치 생성 + 이동
git status                    # 변경사항 확인
git add .                     # 변경사항 스테이징
git commit -m "feat: 설명"     # 커밋
git push origin feature/이름    # 원격에 올리기
# → GitHub에서 Pull Request 생성 → 리뷰 → Merge
```

궁금한 점은 언제든 팀 채널에 편하게 물어보세요! 🙌
